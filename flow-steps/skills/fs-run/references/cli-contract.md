# CLI-контракт flow.py

Движок не вызывает API моделей и не знает, как исполнять целевые скиллы. Он
возвращает задания агенту. Все операции выполняются локально, без сети.

## Вызов

```text
PYTHON /absolute/path/fs-run/scripts/flow.py --project PROJECT COMMAND [OPTIONS]
```

`PROJECT` — существующий корень рабочего Git-дерева. Относительный путь допустим,
но агенту рекомендуется передавать абсолютный. Пути с пробелами нужно заключать
в кавычки средствами используемой оболочки. Поддерживаются Python 3.11+ и Git.

| COMMAND | OPTIONS | Назначение |
|---|---|---|
| `inspect` | — | Вернуть текущее действие; не менять состояние |
| `create` | `--flow FILE` | Создать прогон. FILE — имя из `flows/*.yaml`; при одном файле можно опустить |
| `choose` | `--token TOKEN --option ID` | Сохранить вариант развилки и вернуть `stop` |
| `begin` | `--token TOKEN [--answers FILE]` | Сохранить первую попытку и вернуть `execute_step` |
| `retry` | `--token TOKEN --mode same\|new [--answers FILE]` | Повторить попытку; `same` не принимает новые ответы |
| `confirm` | `--token TOKEN [--message-stdin]` | Подтвердить шаг или запросить разовое сообщение |

FILE с ответами — UTF-8 JSON-объект. Он должен содержать ровно имена `ask` данного
шага; каждое значение — строка. Без `--answers` передаётся `{}`. Движок читает
файл, но не удаляет произвольный пользовательский файл. Для одноразового ввода
создавай его в `.flows/` и удаляй после успешного запуска. Во время `begin`
ответы уже записываются в нужной форме; после выполнения работы обновления нет.

## Ответы

Одна JSON-запись в stdout; UTF-8. Код выхода 0 — операция выполнена или требуется
ответ пользователя. Код 1 — `action: blocked` с `code`, `message` и деталями.
Справка `--help` выводит обычный текст.

| action | Что делать |
|---|---|
| `choose_flow` | Выбрать единственный файл либо спросить пользователя |
| `no_flows` | Остановиться: нужны определения в `flows/*.yaml` |
| `answer_decision` | Показать `question`, получить `options[].id` |
| `prepare_step` | Проверить `skill`, задать `questions`, вызвать `begin` |
| `review_step` | Показать `prompt` и `files`, получить выбор confirm/retry_same/retry_new |
| `execute_step` | Выполнить только возвращённый `prompt` по `skill`, затем остановиться |
| `ask_commit_message` | Спросить сообщение, затем `confirm --message-stdin` с новым token |
| `recover_confirmation` | Вызвать confirm для ранее начатого подтверждения |
| `stop` | Остановиться; следующий узел требует нового `/flow-steps:fs-run` |
| `completed` | Сообщить о завершении |
| `blocked` | Объяснить ошибку; не обходить её ручными правками стейта |

`token` связывает вызов с `runId` и ревизией стейта. Передавай его без изменений.
После каждого ответа используй актуальный token. Повтор старого запроса получает
`stale_token` и ничего не меняет. После ошибки заново вызови `inspect`.

Пример успешно зарегистрированной попытки:

```json
{
  "action": "execute_step",
  "runId": "<идентификатор>",
  "step": "analyze",
  "token": "<идентификатор>:2",
  "skill": null,
  "prompt": "Проанализируй задачу...",
  "state_saved": true,
  "after_execution": "Stop. Present the result and ask the user to invoke the confirmation skill. No state update is needed."
}
```

## Передача сообщения коммита

`confirm --message-stdin` читает весь stdin как UTF-8 текст до EOF. Движок не
показывает терминальный вопрос и не сохраняет сообщение в файлы. Предпочтительно
передать stdin напрямую инструментом запуска процесса. Не используй файл
`--answers`, аргумент командной строки или стейт для сообщения коммита.

Если доступен только shell, допустим literal here-document в Bash или literal
here-string в PowerShell, переданный по pipe. Выбирай разделитель, которого нет
в тексте, и обеспечь UTF-8 кодировку pipe. Это транспорт данных, а не место для
интерполяции текста как кода. Терминальный транскрипт агента может содержать
исходный ответ пользователя; обещание несохранения относится к движку и стейту.

Git получает сообщение через stdin и сам сохраняет его в метаданных коммита
(и может использовать собственные служебные файлы, например COMMIT_EDITMSG).
Движок не изменяет внутреннюю работу Git и не хранит сообщение для повторения.

Если сообщение не задано шагом, новый confirm сначала вызывается **без**
`--message-stdin`. При наличии диффа он вернёт `ask_commit_message`. Не подставляй
ответ из предыдущей неудачной попытки. Если дифф исчез, вопрос больше не нужен.

## Состояние и восстановление

`.flows/` должен быть полностью игнорируемым и не содержать tracked-файлов.
Подготовь `.gitignore` и закоммить настройку до первого рабочего шага. Движок
сам не исправляет конфигурацию Git. Игнорируемые файлы не включаются в коммит.

Прогон содержит снимок `flow.yaml` и `state.yaml`. Помимо `current`, `status`,
`vars`, `rendered` сохраняются служебные `schemaVersion`, `runId`, `revision`,
`flowHash`. `completed: true` отмечает оконченный прогон; рабочие статусы остаются
только `not_started` и `in_progress`.

При подтверждении служебный `pendingCommit` хранит исходный HEAD, ожидаемое дерево
и, когда известен, SHA созданного коммита. Сообщения пользователя в нём нет.
Если процесс прервался, следующий confirm:

1. При прежнем HEAD снимает незавершённую регистрацию и заново обрабатывает
   подтверждение, в том числе запрос сообщения.
2. При однозначно совпадающем созданном коммите и чистом дереве сохраняет переход
   без второго коммита.
3. При несовпадении HEAD/дерева или оставшихся изменениях останавливается.

Если завершение прогона уже сохранено, но удаление активного указателя прервалось,
`inspect` также возвращает `recover_confirmation`; следующий `confirm` только
снимает указатель и возвращает `completed`.

Восстановление предполагает согласованное условие: никто параллельно не делает
посторонние изменения или коммиты в этом рабочем дереве. Хуки не отключаются.
Если хук меняет staged-содержимое, а процесс оборвался до записи SHA коммита,
движок может потребовать ручного выяснения результата вместо догадки.

Запись файлов выполняется через временный файл, flush/fsync и замену. ОС-блокировка
защищает только короткие изменяющие операции и освобождается при завершении
процесса; файл `.flows/lock` можно оставлять. Блокировка не удерживается во время
работы агента или ожидания пользователя. Это не гарантия сохранности при отказе
диска или синхронизации состояния между разными машинами.

`create` сначала сохраняет прогон, затем возвращает действие начального узла.
Если дерево грязное, прогон уже создан, но рабочая попытка ещё не начата. Исправь
причину и используй `inspect`, не создавай второй прогон.
